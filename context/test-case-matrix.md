**How this differs from the companion pytest matrix (75 rows):** one row here is one Postman request, and a request usually asserts several things at once (status, body facts, schema, the shared checks). Rows that pytest parametrizes become either separate requests or one data-driven request (folder 06). The companion's slow expiry test (row 17) and cookie-path rows (4, 14, 26) are left to the pytest suite, as recorded under Open questions.

**Shared checks on every request** (collection-level test script, not repeated below): response time under `{{maxResponseMs}}` (3000 ms); JSON content type whenever there is a body; every 4xx/5xx body is exactly `{"message": <string>}` (the error shape).

## Open questions / follow-ups

- **Known-defect rows (46–58):** each asserts the correct behaviour, from an `(inferred)` rule and so tagged `[Assumption]`; the Expected column records what the API did on 2026-09-29. They run in `99 Known defects`, outside the gating run (see the agent's Project overrides). These are the same 13 defects the companion pytest suite pins as strict xfails.
- **Left to the companion pytest suite on purpose:** the real ~65 s token expiry (companion row 17), the cookie paths (rows 4, 14, 26), JWT claim decoding beyond `exp - iat`, `expiresInMins: 0` and `43200`, and the date-range filter happy path. They add little that is Postman-specific and would slow every CI run.
- **Shared checks** make the error shape part of every negative row, so rows 3 and 24 are the only ones that name it explicitly.
- **Data-driven terms** are chosen to exist in the catalogue as of 2026-09-29; the validation run confirms each one.
- **Out of scope, not gaps:** carts, users, posts and the other resources.
