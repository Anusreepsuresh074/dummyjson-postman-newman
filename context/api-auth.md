# API Authentication

_Generated by get-api-auth on 2026-09-29, from the companion project's `context/api-auth.md` (2026-09-27) and today's live re-check (see `context/api-context.md`, Doc sources). Re-run when the API's auth mechanism changes._

## Auth method(s)

| Endpoint group | Method | Notes |
|---|---|---|
| `POST /auth/login` | None | Credentials in the JSON body; this is where tokens come from. |
| `POST /auth/refresh` | None | No `Authorization` header; the refresh token itself (in the body, or the `refreshToken` cookie) is the credential. |
| `GET /auth/me`, `/auth/products…` (the `/auth/RESOURCE` mirror) | Bearer | `Authorization: Bearer <accessToken>` (docs). The `accessToken` cookie is accepted as an alternative (docs + observed). **This project's primary mechanism is the Bearer header.** |
| Public `/products…` routes | None | No token needed or checked. |

## Swagger/OpenAPI findings

No spec available: `/openapi.json`, `/swagger.json`, `/redoc`, `/api-docs` all return `404` (see `context/api-context.md`), so there is no `securitySchemes` block. The findings below come from the docs pages `https://dummyjson.com/docs/auth` and `https://dummyjson.com/docs` ("Authorizing Resources"), plus live calls to `https://dummyjson.com` on 2026-09-27, which the user approved. The live calls logged in as one of DummyJSON's published test users. Tokens were extracted inside scripts and never printed.

## Auth endpoint(s)

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/login` | Login: issues an access token and a refresh token (JWTs), in the body and as cookies |
| POST | `/auth/refresh` | Token refresh: new access + refresh pair from a refresh token |
| GET | `/auth/me` | Returns the token's user. Not an auth endpoint as such, but the simplest protected call to check whether a token is accepted |

Dependency: `/auth/refresh` needs the `refreshToken` from a previous login or refresh. There is no logout or revoke endpoint.

## Request shape

```
POST /auth/login
Content-Type: application/json

{
  "username": "<username>",
  "password": "<password>",
  "expiresInMins": <integer, optional — default 60>
}
```

```
POST /auth/refresh
Content-Type: application/json

{
  "refreshToken": "<refresh token>",      // optional if the refreshToken cookie is sent
  "expiresInMins": <integer, optional>    // applies to the new ACCESS token (docs)
}
```

```
GET /auth/me
Authorization: Bearer <access token>
```

- **Where credentials come from:** any user listed at `https://dummyjson.com/users` (per the docs); they're public test accounts, not personal ones. Read them from the environment variables `AUTH_USERNAME` / `AUTH_PASSWORD` (local `.env`, which is gitignored; CI repository secrets). Never hardcode them in tests, payloads, or config. `.env.example` should list both names with no values.

## Response validation

- **Login success:** `200`, body fields `id` (int), `username`, `email`, `firstName`, `lastName`, `gender`, `image` (strings), `accessToken`, `refreshToken`. These match the docs example exactly, and no other fields were observed. Both tokens are also set as `Set-Cookie`: `accessToken` and `refreshToken`, each `HttpOnly; Secure`.
- **Tokens are JWTs:** three base64url segments; header `{"alg": "HS256", "typ": "JWT"}`. Claims in both tokens: `id, username, email, firstName, lastName, gender, image, iat, exp`. The two tokens carry the **same claim set**; nothing marks which is which (see token-type states below).
- **Expiry:**
  - Access token: `exp - iat` = `expiresInMins × 60`; the default is 3600 s.
  - `expiresInMins: 0` gives a 30-day token (2592000 s).
  - The maximum is 43200 minutes (30 days).
  - Refresh token: always 30 days (2592000 s), even when a 1-minute access token is requested.
  - Refresh `expiresInMins: 5` → new access token lifetime 300 s.
- **Refresh success:** `200`, body exactly `{accessToken, refreshToken}` (docs example; observed). Works with the token in the body, or with only the `refreshToken` cookie.
- **Failure cases (all bodies are `{"message": "<string>"}`):**

  | Call | Status | `message` |
  |---|---|---|
  | Login, wrong password | 400 | `Invalid credentials` |
  | Login, unknown username | 400 | `Invalid credentials` (identical, so it doesn't reveal which usernames exist) |
  | Login, `username` and/or `password` missing | 400 | `Username and password required` |
  | Login, `expiresInMins: 43201` or `-1` | **500** | `Maximum access token expire time can be 43200 minutes` |
  | Protected call, no token | 401 | `Access Token is required` |
  | Protected call, expired token | 401 | `Token Expired!` |
  | Protected call, malformed token (`abc.def.ghi`) | **500** | `invalid token` |
  | Protected call, forged signature | **500** | `invalid signature` |
  | Protected call, `Authorization: Basic <token>` | **500** | (not captured) |
  | Protected call, raw token without `Bearer ` | **200** | accepted |
  | Protected call, refresh token as Bearer | **200** | accepted |
  | Refresh, invalid token string | 403 | `Invalid refresh token` |
  | Refresh, no token | 401 | `Refresh token required` |
  | Refresh, access token in place of refresh token | **200** | new pair issued |
  | Refresh, reusing an already-used refresh token | **200** | accepted (no rotation) |

  Bold statuses differ from what a correct implementation would return (`400`/`401`/`403`). They are recorded as observed; `api-test-design` decides how to treat them. `429` rate limiting was not observed and is not documented.

## Token storage & variable naming (Postman)

- **Credentials:** `username` and `password` are environment variables with **empty values in the committed file**. `scripts/run-newman.sh` fills them at run time with `--env-var` from `AUTH_USERNAME` / `AUTH_PASSWORD` (a gitignored `.env` locally, repository secrets in CI).
- **Tokens:** the `Log in with valid credentials` request's test script saves `accessToken` and `refreshToken` with `pm.environment.set(...)`. Later requests send `Authorization: Bearer {{accessToken}}`. Newman never writes the environment back to disk (no `--export-environment`), so tokens live in memory for one run only.
- **Masking:** DummyJSON's `/auth/me` returns the user's `password` and other secrets in its body, and login and refresh bodies carry JWTs. The HTML report is therefore produced with `--reporter-htmlextra-skipSensitiveData` (no headers or bodies in the report), no JSON reporter is used, and `scripts/check-secrets.sh` scans every report for the password and for JWT-shaped strings before anything is published.
- **Test assertions:** never compare a token or the password with `eql` in an assertion message; check presence, type and shape instead, so a failure message can't print a secret.
- **Cookies are off.** Login also sets the tokens as cookies; Newman's cookie jar would send them on every later request and make "no token" cases pass silently (seen in the first validation run). The collection sets `protocolProfileBehavior.disableCookies: true`, so a request is authenticated only by the headers it declares.
- **Least privilege:** the only privilege level is "a published user"; one user is enough.

## Token reuse & negative auth states

- **Reuse:** one login at the start of `01 Auth` sets the tokens for the whole run. Folders that need a token and may run alone (`05 Protected routes`, `99 Known defects`) log in themselves first, with a request whose tests save the same variables.
- **Lifetime:** logins ask for `expiresInMins: 30`, far longer than a run (under 1 minute), so no mid-run refresh is needed.
- **Expired token:** the real ~65 s expiry wait is **not** repeated in this collection, to keep every CI run short. It stays covered by the companion pytest suite (`test_expired_token_rejected_then_refresh_recovers`).
- **Negative states for `auth-authz` cases:**


  | State | How to obtain it |
  |---|---|
  | Missing token | Omit the `Authorization` header (and send no cookie). |
  | Invalid (malformed) token | A value with a JWT's shape but not a JWT, e.g. `abc.def.ghi`. |
  | Invalid (forged signature) | Take the real session access token and change a character of its signature segment only, so the claims stay valid. Never use an unrelated real token. |
  | Wrong scheme | Send the real token as `Authorization: Basic <token>`, or as the raw value without `Bearer `. |
  | **Expired token** | **Genuinely obtainable:** log in with `expiresInMins: 1`, wait until the token's own `exp` + a few seconds (~65 s), then call. Confirmed live today: `401 "Token Expired!"`. This is a real ~65 s wait; see Token reuse below for how this project handles it. |
  | Wrong token type | Send the session *refresh* token as the Bearer token; send the *access* token as `refreshToken`. |
  | Invalid refresh token | Any non-JWT string as `refreshToken`. |
  | Wrong-role / insufficient-scope | **Not applicable.** No role or scope claim exists and every published user can call every route. |
  | Permission/plan-scoped denials | **Not applicable.** No org, branch, permission or plan concept exists. |

## Open questions / follow-ups

- **No logout/revoke endpoint exists**, so "a revoked token is rejected" cannot be tested.
- **Refresh tokens don't rotate** and either token type is accepted in place of the other (re-confirmed 2026-09-29). These are recorded as known defects.
- **The 500 responses** (malformed and Basic-scheme tokens; out-of-range `expiresInMins`) aren't documented; re-confirmed 2026-09-29.
- **Rate limit:** not documented, but the companion performance project found **100 requests per 10 s per IP** in DummyJSON's source code and confirmed it live (`x-ratelimit-remaining` header). The collection sends about 45 requests with a 100 ms delay between them, far below the limit.
